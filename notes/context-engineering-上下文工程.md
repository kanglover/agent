# 上下文工程（Context Engineering）核心笔记

> 沉淀时间：2026-06-24
> 来源：业界最佳实践精华整理（Claude Code、Manus、LangChain、Kiro）

---

## 一句话总结

Agent 失败的根本原因不是模型不行，而是给的信息不对、不全、不及时。上下文工程就是系统性地解决这个问题。

---

## 核心是什么？

**上下文工程** = 研究「喂给 AI 什么信息、怎么喂」的学问。

> 类比：AI 就像临时员工，每次开始工作前要做「背景介绍」。介绍得好，干得好；介绍得烂，一脸懵。上下文工程就是把这个「背景介绍」做到极致的方法论。

### 和提示词工程的区别

| | 提示词工程 | 上下文工程 |
|--|-----------|-----------|
| **关注点** | 怎么把一句话说得好 | 怎么把完整背景给到 AI |
| **范围** | 只管任务描述怎么写 | 管文档、规则、记忆、工具… |
| **类比** | 贴一张便签 | 写一部完整剧本 |

---

## 上下文的 7 个组成部分

| 组件 | 是什么 | 类比 |
|------|--------|------|
| **系统提示词** | 告诉 AI 整体规则和行为 | 员工手册 |
| **用户提示词** | 当下的具体任务 | 今天的任务单 |
| **短期记忆** | 本次对话历史 | 这次会议的记录 |
| **长期记忆** | 跨对话积累的知识 | 员工档案 |
| **RAG 检索信息** | 临时查来的外部资料 | 临时查阅的文件 |
| **可用工具** | AI 能调用的功能 | 员工工具箱 |
| **结构化输出** | 规定 AI 的回复格式 | 报告模板 |

## 长上下文的核心问题：Context-Rot（上下文腐蚀）

随着对话越来越长，AI 的注意力会「稀释」，出现：

- ❌ 被错误信息带偏，越走越歪
- ❌ 关键信息被淹没，记不住重点
- ❌ 信息冲突，行为变得不可预测
- ❌ 重复内容太多，AI 不知道该干嘛

---

## 解决方案：LangChain 的四类方法

| 方法 | 思路 | 类比 |
|------|------|------|
| **Offload（外放）** | 把大量信息存到外部，只给 AI 一个「指针」 | 把书放书架，只告诉 AI 书名 |
| **Retrieve（检索）** | 用 RAG 技术，按需取相关信息 | 用搜索引擎，只查有用的 |
| **Compress（压缩）** | 裁剪冗余，只保留关键 token | 把报告摘要成一页纸 |
| **Isolate（隔离）** | 拆成子任务，分给不同子 Agent 各自处理 | 不同部门各自处理自己的事 |

## 顶级产品的工程实践

### Claude Code 的四大实践

| 实践 | 解决什么问题 | 怎么做 |
|------|------------|--------|
| **三层记忆架构** | 对话太长信息会丢 | 短期对话 + 智能压缩（92% 阈值触发）+ CLAUDE.md 长期记忆 |
| **实时 Steering** | 任务中途不能调整方向 | 异步消息队列，随时打断和恢复 |
| **分层多 Agent** | 复杂任务单个 Agent 撑不住 | 主 Agent 调度，子 Agent 独立执行（最多 10 个并发） |
| **动态上下文注入** | AI 不知道你在说哪个文件 | 自动识别文件引用，注入相关内容（最大 20 文件 / 8K Token） |

---

### Manus 的六大优化

| 优化 | 核心思路 | 为什么这么做 |
|------|----------|------------|
| **围绕 KV 缓存设计** | 保持上下文前缀稳定，不放时间戳 | 命中缓存成本降低 **10 倍**（$3 → $0.3 / 百万 token） |
| **遮蔽而非移除工具** | 用状态机控制可用工具，不动态增删 | 动态改工具会使缓存失效，模型也会困惑 |
| **文件系统当记忆** | 信息写文件，只给 AI 路径引用 | 突破上下文窗口长度限制，信息不丢失 |
| **复述目标到末尾** | 每步把待办列表重写到上下文末尾 | 防止 AI 执行 ~50 步后忘了最初目标 |
| **保留错误信息** | 不删除失败的尝试记录 | 让 AI 从错误中学习，不重蹈覆辙 |
| **增加少样本多样性** | 给示例加一点格式变化 | 防止 AI 过度模仿固定模式导致行为僵化 |

## Spec-Driven Development（规范驱动开发）

### 传统方式 vs 新范式

- ❌ **Vibe Coding**：`随手写 Prompt → 直接生成代码`
- ✅ **Spec-Driven**：`Prompt → 需求文档 → 系统设计 → 任务清单 → 代码`

### 三个核心文档（以 Kiro 为例）

| 文档 | 内容 |
|------|------|
| `requirement.md` | 用户故事（WHEN [条件] THE SYSTEM SHALL [行为]） |
| `design.md` | 技术架构、接口定义、数据库结构、前端实现 |
| `tasks.md` | 拆分成可执行的 TODO 清单，实时追踪状态 |

**好处**：AI 有完整上下文，生成代码质量更高，更易维护，适合大型项目和多人协作。

## 未来方向：从上下文工程 → 环境工程

| 阶段 | 核心 | AI 的角色 |
|------|------|----------|
| **提示词工程** | 写好一句话 | 被动执行指令 |
| **上下文工程** | 填好信息背景 | 被动接受信息 |
| **环境工程（未来）** | 构建 AI 能感知和影响的完整世界 | 主动感知 + 主动塑造 |

> 现在的 AI 就像关在屋子里只能收短信的人。未来要给它完整的五感。

---

## 适用场景

- 构建 Agent 系统时，优先思考「信息怎么流向模型」
- 多轮对话 / 长任务：用 Offload + Compress 控制上下文长度
- 工具很多时：用 Retrieve 按需注入，而非全量塞入
- 复杂任务：用 Isolate 拆分子 Agent，避免上下文污染
- 降本增效：围绕 KV 缓存设计，保持前缀稳定
